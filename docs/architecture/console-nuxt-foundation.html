A fundação do novo Console

O novo Design System exige reconstruir a apresentação de todo o Console. É a janela para corrigir a causa raiz: o projeto atual não foi desenhado para manutenibilidade, performance nem segurança. Quatro andares, duas decisões centrais, e fronteiras que o lint e os testes verificam a cada build.

01 As camadas da aplicação — o big picture

A aplicação tem quatro andares. No topo, o domínio: uma pasta por seção do Console. Abaixo, o módulo core, que entrega todas as capacidades compartilhadas. Depois a fundação (design system, cache, servidor) e, na base, as APIs. A regra que sustenta o desenho: a dependência só aponta para baixo.

02 O ciclo de um request — onde a Shell é decidida

Este fluxo substitui a cadeia de oito guards do console-kit. O ponto crítico é o passo 6: a mesma URL pode servir a tela default ou a versionada, e a escolha é feita no servidor, a cada request, com o contexto fresco da conta.

1GET /applications/edit/123 o browser envia o cookie de sessão junto
Nitro na Azion Edge — executa no servidor, uma vez por request
2Plugins de servidor o tema vem do cookie e já é aplicado no HTML; preconnect das fontes
3O AppContext é composto
  1. o transporte de credencial resolve a identidade a partir das claims do JWT
  2. o provider OpenFeature avalia as flags com esse contexto
  3. o tema vem do cookie
uma composição, provida pela AppShell — refeita na troca de conta, não a cada navegação
4O guard auth.global verifica a identidade sem identidade, redireciona ao login guardando a rota de retorno
5A rota estável monta o ShellResolver rota canônica do resource, a mesma nos dois modos
6resolveMode() devolve o modo e o motivo
  1. o resource declara que suporta versões
  2. a feature flag está ligada para a conta
  3. o usuário tem permissão para o modo versionado
  4. a API oferece a capability necessária
DefaultShell modo default — versionamento desligado, sem suporte ou sem permissão
VersionShell modo versioned — versionamento ligado para a conta
7HTML pronto, com o estado da sessão embutido nada precisa ser buscado de novo no cliente
8O browser hidrata mesma Shell e mesmo tema que o servidor pintou — sem flash de tema, sem divergência de hidratação, sem buscar dados de novo

Figura 2. Os passos 2 a 7 rodam no servidor, uma vez por request. O AppContext do passo 3 é a fonte única de sessão, permissões e feature flags — no console-kit atual essa informação tem duas fontes de verdade que se dessincronizam, e a rota chega a discordar do menu.

Por que isso importa

Nas navegações seguintes dentro do app, o mesmo resolveMode() roda no browser com o contexto já hidratado. Trocar de conta gera um contexto novo e uma decisão nova, sem recarregar a página.

No console-kit atual

Essa escolha é um ternário dentro do import da rota, avaliado uma única vez por sessão: trocar de conta mantém a tela errada até recarregar a página.

Os dois modos são escolha do cliente, não estágios de migração

O que o passo 6 decide é qual modo de operação está ativo para aquele cliente — e essa é uma escolha permanente e reversível, não uma etapa de rollout.

versionamento habilitado → VersionShell

O cliente trabalha com versões, estados, build e deploy. Salvar grava um rascunho, que só passa a valer depois de publicado.

Exige V6 — versionamento só existe nessa versão da plataforma.

versionamento desabilitado → DefaultShell

Persistência direta: editar, validar e salvar. A configuração salva passa a ser efetiva sem build nem deploy.

Modo permanente e suportado, não estado legado.

O que decorre disso

A DefaultShell recebe o mesmo investimento e cobertura de testes que a VersionShell. E, como o cliente pode alternar nos dois sentidos, a troca de modo durante a sessão é um fluxo real: com alterações pendentes ou operação assíncrona em andamento, a troca automática é bloqueada e o usuário decide — e um rascunho versionado nunca vira salvamento direto silenciosamente.

Por que jwt e não session

JWT foi criado para dispensar sessão no servidor: as claims estão dentro do token. Chamar o modo de session afirmaria o oposto do mecanismo — e pelo mesmo motivo o AppContext carrega identity, não session.

O trade-off é explícito

Adotar bff-session é abrir mão de stateless para tirar a credencial do alcance do JavaScript. Não é melhoria gratuita, é troca — e por isso fica como opção declarada, não como padrão.

04 Camada de serviços — a fachada única e a escolha da instância

O console-kit tem quatro gerações de serviço convivendo e cinco mecanismos diferentes decidindo qual usar conforme a conta. A fundação reduz isso a uma hierarquia de seis níveis e a dois pontos de decisão auditáveis.

a hierarquia — do abstrato ao concreto
N0Contratos — a fachada que todo serviço satisfaz list · get · create · update · remove — os mesmos nomes em todos os resources
N1apiFetch — o único cliente HTTP monta a URL pela versão declarada, anexa a credencial da estratégia ativa e o id de correlação
N2ResourceService — a classe base fluxo fixo: chama a API, passa pelo adapter e invalida o cache — é o único lugar do sistema que invalida
N3createResourceAdapter — a fábrica transformadores puros de payload; é o único lugar que conhece o formato de dados da API
N4O resource concreto — cerca de vinte linhas declara a URL base, a versão da API, o editor e as chaves de cache. Nada mais.
N5Quem consome os serviços DefaultShell, tela de listagem e a VersionShell — todos falam com a mesma fachada
extensão versionada

A VersionShell estende esta mesma classe base e acrescenta o ciclo de vida das versões.

como a instância certa é escolhida
1AppContext sessão, permissões, modelo de configuração e tema
2resolveMode() devolve o modo função pura: contexto + capacidades do resource → ShellMode e motivo
3A Shell provê o ResourceContext com modo e referência já fixados — o miolo não os vê
4O serviço não guarda estado nada do usuário fica preso nele entre requests
5A chamada usa a fachada canônica a tela nunca escolhe endpoint nem versão
6apiFetch resolve a URL da versão declarada pelo adapter — uma linha de código
API da plataforma — v3, v4 ou v6 a versão da conta age uma única vez, no passo 2; a versão da API é uma declaração no adapter
Hoje

Essa escolha está espalhada por cinco mecanismos diferentes — inclusive dentro de adapters — e a versão da API aparece cravada em 56 pontos do código.

Figura 4. O padrão não é invenção nova: é a generalização do VersionServiceBase e do createVersionAdapter que o próprio console-kit já provou em produção no VersionShell. A diferença é que ali eles atendem só aos recursos versionados; aqui, atendem todos.

O modo é o discriminante, e é um tipo

Toda a diferença entre operar no modo default e operar sobre uma versão cabe num tipo. Um booleano obrigaria cada chamada a lembrar de passar o versionId e permitiria o estado inválido “versionado sem versão”.

// app/core/contracts/shell-mode.ts
// Dois eixos separados. O modo decide a Shell; a referencia identifica.
export type ShellMode = 'create' | 'default' | 'versioned'

export interface ResourceRef {
  resourceId?: Id     // ausente em create
  versionId?: Id      // presente somente em versioned
}

// A Shell e DERIVADA do modo. Duas Shells para tres modos.
export const shellFor = (mode: ShellMode) =>
  mode === 'versioned' ? VersionShell : DefaultShell

// A URL, a queryKey e o payload derivam de modo + referencia.
export const resourcePath = (mode: ShellMode, ref: ResourceRef, base: string) =>
  mode === 'versioned'
    ? `${base}/${ref.resourceId}/versions/${ref.versionId}`
    : `${base}/${ref.resourceId ?? ''}`
Três modos, duas Shells

shellFor(mode) devolve VersionShell para versioned e DefaultShell para new e default. Criar não é uma Shell: é um modo. O editor, o schema e a validação são os mesmos — muda a ação, create em vez de save.

E login não é uma Shell

Login acontece fora da AppShell: sem sessão, sem conta, sem navegação. É ausência de moldura, não uma moldura diferente — uma página com outro layout.

O contexto do resource — onde a Shell troca o miolo

O modo não é passado de mão em mão: é um campo do contexto do resource, um único contrato que a Shell provê e o miolo consome. Miolo é o que está sendo operado — editor, tabs, listagens de sub-recurso. A Shell troca o miolo mantendo o contrato.

// app/core/contracts/resource-context.ts
export const RESOURCE_CONTEXT = Symbol('resourceContext')

export interface ResourceContext<TEntity> {
  mode:         Readonly<Ref<ShellMode>>         // o que a Shell decidiu
  ref:          Readonly<Ref<ResourceRef>>       // o que esta sendo operado
  resource:    Readonly<Ref<TEntity | null>>     // o miolo em operacao
  service:     ResourceService<TEntity>         // com modo e referencia fixados
  state:       Readonly<Ref<State>>              // um estado na Default, o ciclo na Version
  readOnly:    Readonly<Ref<boolean>>
  actions:     Readonly<Ref<ActionKey[]>>        // estado ∩ capacidade declarada
  permissions: PermissionContext
  dispatch(action: ActionKey, payload?: unknown): Promise<void>
}

// Defaults seguros: o componente funciona fora de uma Shell.
export const useResourceContext = <T>() =>
  inject<ResourceContext<T>>(RESOURCE_CONTEXT, DEFAULT_CONTEXT)

Hoje: chave por resource

O resource é provido por string — uma chave diferente por seção. O componente precisa saber de qual resource é filho para injetar.

Defaults seguros

Fora de qualquer Shell, o componente recebe estado editável e nenhuma ação. É o que permite migrar tela por tela sem quebrar o que ainda não foi migrado.

O que o contexto resolve além da simetria

Trocar de versão, ou de conta, passa a ser prover um contexto novo — não remontar a árvore. Hoje o remount forçado por chave é obrigatório porque os identificadores são capturados por valor na montagem, e o custo é perder o estado da interface.

useResourceService

O consumidor recebe o service com modo e referência já fixados e não os vê. É o que permite a mesma listagem de sub-recurso funcionar nas duas Shells sem uma linha de diferença — eliminando a facade escrita à mão por sub-recurso.

07 Por que reconstruir — quatro subsistemas medidos

O gatilho é o novo Design System: reconstruir a apresentação de todo o Console é inevitável. A pergunta é se vamos reconstruir sobre a mesma base. O projeto atual não foi desenhado para manutenibilidade, performance nem segurança. Cresceu por convenção, e convenção sem verificação automática diverge. Abaixo, a divergência medida em quatro subsistemas, com o atributo que cada um compromete. Cada número é contagem no repositório.

camada de serviços · manutenibilidade
  • Três padrões na camada de serviços: 145 arquivos no padrão funcional legado, 63 classes estendendo a base, 6 híbridos
  • Quem escreve um resource novo escolhe entre três estilos; nenhum é errado, então todos persistem
  • 29 ListViews importam o mesmo par de templates de chrome; 114 de 437 views montam o chrome direto
  • 45 views declaram array de actions inline; 44 reimplementam a exclusão; 25 embutem o service no objeto da ação
  • 206 views importam service direto; as dez maiores têm de 814 a 1.456 linhas
apresentação e ações · manutenibilidade e performance
  • Actions e colunas montadas por tela, não derivadas de contrato: o resource carrega o conjunto completo independente de estado e permissão
  • O custo é pago no bundle e no primeiro render, para ações que muitas vezes não podem ser executadas
  • Sessão e flag resolvidas no cliente, em cascata: requisições bloqueantes antes do primeiro pixel
  • Sem moldura persistente, navegar remonta chrome que deveria ser estável
  • Invalidação de cache espalhada — refetch redundante, sem dono
credencial e sessão · segurança
  • A reescrita de cookie na borda descarta o HttpOnly: credencial de longa duração legível por JavaScript
  • Credencial escolhida por efeito colateral em estado global — o modo ativo não é auditável
  • Nenhum interceptor de resposta: a expiração só é percebida ao navegar
  • Booleano em armazenamento local como porteiro de rota
  • Logout não limpa cache nem estado do cliente
roteamento de rede · manutenibilidade e segurança
  • Sete mecanismos podem definir o prefixo de uma chamada — 87 baseURL em quatro grafias, 49 helpers de base, 70 overrides no call site
  • Oito formas de URL, três produzindo a mesma URL: não existe forma correta a copiar
  • Tabela de roteamento duplicada com precedência oposta — e nenhum teste falha se só uma for editada
  • Versão declarada três vezes em desacordo: no path, no Accept e numa regra de edge que força versão 3
O padrão se repete nos quatro subsistemas

Em todos os casos a decisão certa existe em algum lugar do código — mas sem dono único e sem enforcement. Então cada feature re-decide, e o sistema diverge. Não é falta de cuidado: é ausência de arquitetura que torne a decisão obrigatória.

O que o roteamento de rede exige da fundação

Três requisitos, e o desenho está na seção 04. O prefixo é declaração, nunca literal — enquanto puder ser escrito em sete lugares, será. A tabela de roteamento tem uma fonte só, com as duas configs como artefato gerado e verificação de acordo no CI. E serviço e contrato são eixos distintos: o desacordo das três declarações de versão mostra que v3, v4 e v6 são serviços com contratos diferentes, não versões de um mesmo — o que invalida a premissa da decisão pendente sobre o nome do eixo.

A contraprova já existe no Console

O versionamento foi entregue recentemente e cumpriu o papel: passou a suportar o ciclo de vida versionado em todos os resources com custo marginal por resource e sem drift entre eles. Ele tem dono único, contrato explícito e verificação automática contra fork — e é exatamente por isso que funcionou. O que esta fundação faz é generalizar esse mesmo padrão para autenticação, serviços, roteamento e apresentação.

09 Repositório aberto e whitelabel

O repositório é de código aberto e precisa permitir whitelabel. Isso não é só licença: é restrição de desenho. O deploy vive em outro repositório, com infraestrutura como código.

Por que isso testa a arquitetura

Se uma constante não puder ser externalizada com valor de exemplo, é porque existe regra de negócio escondida onde deveria haver configuração. A exigência do whitelabel funciona como verificação: o que não sai para constante é acoplamento que ninguém declarou.

10 Como a Shell sabe quais ações mostrar

Uma Shell só pode oferecer ações válidas, e duas coisas independentes determinam validade: o estado em que a coisa está, e se o resource implementa aquela ação. Uma versão em build não aceita edição por causa do estado; um resource sem arquivamento não oferece Archive por causa da implementação.

A dificuldade é que a Shell é genérica e o resource é específico. A Shell não pode importar código de resource — se pudesse, cada resource novo mexeria na Shell.

O que é um barramento de comandos

O Console atual resolve isso com um barramento. Vale explicar, porque é o mecanismo que substituímos e o termo não é autoexplicativo: um barramento é um objeto central onde o componente interno registra funções sob um nome — SAVE, ARCHIVE — e onde a Shell dispara aquele nome sem saber quem vai atender. Inversão de dependência: a Shell depende do barramento, nunca do resource.

A Shell então cruza duas listas — as ações que o estado permite e as que foram registradas. O que está nas duas aparece na tela. Esse cruzamento é a ideia certa e nós mantemos. O que trocamos é o registro por nome.

Problema do registro por nomeConsequênciaNa fundação
O registro é uma tabela reativa de comportamento sutil Trocar o tipo de reatividade inverte o resultado: formulário válido fica com o botão desabilitado. Documentado como armadilha conhecida. Objeto comum, sem estado reativo intermediário
Disparar um nome sem quem atenda só falha executando O erro aparece para o usuário, não para quem escreveu o código. Método ausente é erro de compilação
Navegação precisou virar comando com função vazia Existe um comando que não faz nada, só para o cruzamento incluir o botão. Navegação não é capacidade e sai do conjunto

Por que separar ausente de desabilitado

O estado é dado, a máquina é função

A máquina não guarda estado: responde o que é permitido a partir de um estado que vem de fora. Isso a torna testável por enumeração — todos os estados contra todos os resources — sem montar componente e sem simular API.

A matriz: a fonte única do que é permitido

A máquina do modo versionado é uma tabela. Cada linha é um estado e lista as ações permitidas nele. Nada fora da tabela decide — a barra de ações, o menu da versão e o cabeçalho leem dela.

Por que draft não pode sofrer deploy

promote não está na linha de draft. O botão não é renderizado — não existe desabilitado, não existe condicional na Shell, não existe verificação no componente. A ausência na tabela é o controle.

Por que ready não pode mais ser alterada

Dois controles independentes. isEditable(ready) é falso → readOnly entra no ResourceContext e todo campo fica desabilitado. E save não está na linha de ready → não existe ação que persista. Um só não bastaria.

// app/versioning/machine.ts — modulo puro: constantes e funcoes.
const STATE_ACTIONS: Record<VersionState, ActionKey[]> = {
  draft:    ['save', 'saveAndBuild', 'newVersionFrom', 'remove'],
  queued:   ['cancelBuild'],
  building: ['cancelBuild'],
  ready:    ['newVersionFrom', 'archive', 'remove', 'promote'],
  active:   ['newVersionFrom', 'archive', 'remove', 'promote', 'rollback'],
  archived: ['newVersionFrom', 'remove'],
  canceled: ['save', 'saveAndBuild', 'newVersionFrom', 'remove'],
  error:    ['save', 'saveAndBuild', 'newVersionFrom', 'remove']
}

const EDITABLE: VersionState[] = ['draft', 'canceled', 'error']

export const versionMachine = {
  initial: 'draft',
  allowedActions: (s) => STATE_ACTIONS[s] ?? [],   // desconhecido -> []
  isEditable:     (s) => EDITABLE.includes(s)
}
A máquina é porteiro, não executor

A matriz diz o que pode ser oferecido; ela não faz a transição. Quem muda o estado é o backend — o cliente executa a ação, o serviço invalida o cache e o novo estado chega no refetch. Por isso a Shell nunca escreve estado, e por isso a validação no backend não é redundante: é a autoridade.

O que NÃO se toca

As Shells (leem a matriz, não enumeram ações), o ShellResolver e o resolveMode (decidem modo, não ações), os outros resources, as rotas e o middleware.

O que garante que ninguém contorne a matriz

Um teste de enumeração: para cada estado e cada resource, comparar o conjunto resolvido com o esperado. Como o cruzamento é função pura, não monta componente nem simula API — e falha no CI se alguém acrescentar condicional dentro de uma Shell.

Na fundação: a presença do método é o registro

// O opcional (?) declara: este resource pode nao implementar esta acao.
export interface ResourceCapabilities {
  save(): Promise<void>
  build?(): Promise<Job>
  cancelBuild?(): Promise<void>
  newVersionFrom?(): Promise<{ id: Id }>
  archive?(comment: string): Promise<Job>
}

// O cruzamento, agora verificavel em compilacao:
// o estado permite  E  o resource implementa.
export const availableActions = (state: State, caps: ResourceCapabilities) =>
  allowedActions(state).filter((a) => typeof caps[a] === 'function')
Por que é mais forte

Com nomes soltos, um comando renomeado só falha quando o usuário clica. Com métodos, o compilador recusa antes do build. O comportamento na tela é o mesmo; muda quando o erro é descoberto.

O que não muda

O cruzamento continua sendo falha fechada: estado desconhecido produz lista vazia de ações, nunca a lista completa. É a decisão do Console atual que mais vale preservar.

As abas são uma prop, não código dentro do scaffold

O scaffold recebe o array de abas numa prop, itera e monta o que vier. Não sabe quantas abas existem, quais componentes carregam, nem se há sub-recursos. A consequência: acrescentar um resource não altera nenhum arquivo de app/core — e o Console atual já tem um teste que falha se isso acontecer.

Resource sem abas — nenhum artefato novo

O scaffold já tem a prop bare. O resource passa uma única entrada de aba. Criar uma segunda forma de montar a tela repetiria o problema das duas landings que a seção 07 aponta.
